# استقرار روی سی‌پنل با PHP و بدون ترمینال

این پروژه Laravel 12، Inertia 2، Vue 3، Vite و پنل Filament دارد. زبان پیش‌فرض `en` و زبان‌های دیگر `fa` و `ar` هستند. مطابق درخواست جدید، ورود به دامنهٔ اصلی همیشه به انگلیسی هدایت می‌شود؛ زبان مرورگر یا session آن را تغییر نمی‌دهد. محتوای واقعی و آدرس‌های فارسی/عربی حفظ می‌شوند.

HTML اولیهٔ صفحات با Blade و داده‌های عمومی همان کنترلرها در هر درخواست PHP ساخته می‌شود. متن مقاله، پروژه، خدمات، بخش‌های صفحه، تصاویر و لینک‌ها داخل بدنهٔ HTML هستند. Node روی هاست لازم نیست. Vue با `createApp` محتوای Blade را در همان ریشه جایگزین می‌کند؛ این HTML خروجی Vue SSR نیست و نباید hydrate شود. حالت بدون JavaScript یک چیدمان خواندنی ساده دارد؛ پس از نصب Vue، طراحی و تعاملات موجود سایت اجرا می‌شوند. هر دو حالت از دادهٔ یکسان و فیلترهای انتشار یکسان استفاده می‌کنند و تشخیص ربات وجود ندارد.

## آماده‌سازی روی کامپیوتر توسعه

PHP سازگار با `composer.lock`، Composer و Node فقط روی کامپیوتر توسعه لازم‌اند. دستورات زیر برای کامپیوتر توسعه‌اند، نه هاست:

```sh
composer install --no-interaction --prefer-dist
npm ci
npm run build
vendor/bin/pest --compact
php scripts/build-cpanel.php /tmp/sdk-cpanel-release-1
```

نام پوشهٔ بسته باید جدید باشد. اسکریپت بسته‌بندی به دیتابیس و `.env` اصلی دست نمی‌زند. `vendor` تولید را در پوشهٔ موقت جداگانه با `--no-dev` آماده می‌کند. فایل `/tmp/sdk-cpanel-release-1.zip` آمادهٔ آپلود است؛ داخل آن:

| مسیر | مقصد و کاربرد |
| --- | --- |
| `sahra/` | برنامهٔ خصوصی، کنار `public_html` و خارج از ریشهٔ وب؛ شامل `app`، `bootstrap`، `config`، `database/migrations`، `lang`، `resources`، `routes`، `vendor` و پوشه‌های خالی `storage` |
| `public_html/` | فایل‌های عمومی، `.htaccess`، `index.php` مخصوص سی‌پنل، `build/manifest.json` و تمام `build/assets`، فونت‌ها، تصاویر و دارایی‌های Filament |
| `sahra/.env.example` | الگوی تنظیمات تولید، بدون کلید و رمز واقعی |

بسته شامل `.env` واقعی، دیتابیس محلی، رسانه‌های آپلودشده، فایل‌های خصوصی، لاگ‌ها، کش توسعه، `public/hot`، `node_modules` یا بستهٔ SSR نیست. رسانه‌های فعلی را جداگانه و با حفظ فایل‌های هاست منتقل کنید. پوشهٔ `public/build` در Git نادیده گرفته می‌شود، اما داخل ZIP وجود دارد.

## آپلود با File Manager

۱. از فایل‌ها، `.env`، دیتابیس و رسانه‌های فعلی با ابزارهای سی‌پنل نسخهٔ پشتیبان بگیرید. در ارتقای سایت موجود، `.env`، `APP_KEY`، دیتابیس و فایل‌های آپلودشده را حفظ کنید.

۲. در MultiPHP Manager نسخهٔ PHP سازگار، ترجیحاً 8.3 یا 8.4، انتخاب کنید. افزونه‌های موردنیاز Composer را فعال کنید؛ از جمله `pdo_mysql`، `mbstring`، `intl`، `fileinfo`، `dom/xml`، `curl`، `openssl` و `zip`. برای تولید نسخه‌های تصویر، GD با JPEG/WebP و در صورت پشتیبانی AVIF لازم است. بدون GD تصویر اصلی توسط PHP برگردانده می‌شود.

۳. ZIP را در پوشهٔ حساب، مثلاً `/home/ACCOUNT`، استخراج کنید تا این ساختار ایجاد شود:

```text
/home/ACCOUNT/sahra/
/home/ACCOUNT/public_html/
```

برای دامنهٔ افزوده یا ریشهٔ وب متفاوت، فایل `public_html/index.php` را در File Manager باز کنید و `$applicationPath` را به مسیر واقعی برنامهٔ خصوصی تغییر دهید. این فایل مسیر عمومی Laravel را روی همان پوشهٔ عمومی تنظیم می‌کند تا manifest و دارایی‌ها درست پیدا شوند. فقط پوشهٔ عمومی باید از وب قابل دسترسی باشد.

۴. در نصب تازه، `sahra/.env.example` را به `sahra/.env` کپی کنید. در ارتقا، فقط تنظیمات لازم را در `.env` موجود به‌روز کنید:

```dotenv
APP_ENV=production
APP_DEBUG=false
APP_LOCALE=en
APP_FALLBACK_LOCALE=en
APP_URL=https://sahramarketing.com
SEO_CANONICAL_ORIGIN=https://sahramarketing.com
INERTIA_SSR_ENABLED=false
SESSION_DRIVER=file
SESSION_SECURE_COOKIE=true
CACHE_STORE=file
QUEUE_CONNECTION=sync
FILESYSTEM_DISK=public
PUBLIC_STORAGE_ROOT=/home/ACCOUNT/public_html/storage
```

دامنه و ACCOUNT را با مقادیر واقعی جایگزین کنید. `.htaccess` فعلی برای `sahramarketing.com` تنظیم شده؛ برای دامنهٔ دیگر، قواعد HTTPS و www آن را نیز با دامنهٔ واقعی هماهنگ کنید. گواهی SSL باید فعال باشد. برای ورود پیش‌فرض انگلیسی، `APP_LOCALE=en` باشد؛ در این پروژه fallback نیز انگلیسی است. `APP_KEY` موجود را حفظ کنید. فقط برای نصب تازه، روی کامپیوتر توسعه با دستور زیر یک کلید بسازید و در `.env` وارد کنید:

```sh
php -r 'echo "base64:".base64_encode(random_bytes(32)).PHP_EOL;'
```

۵. مشخصات دیتابیس MySQL/MariaDB را از MySQL Databases سی‌پنل وارد کنید؛ کاربر باید مجوزهای دیتابیس خودش را داشته باشد. رمزها فقط داخل `.env` خصوصی قرار گیرند. SMTP و `CONTACT_NOTIFICATION_EMAIL` را با مقادیر واقعی تنظیم کنید. صف `sync` اعلان‌ها را در همان درخواست PHP اجرا می‌کند و به worker دائمی نیاز ندارد؛ ارسال واقعی ایمیل به تست روی هاست نیاز دارد.

۶. مجوز نوشتن برای `sahra/storage`، `sahra/bootstrap/cache` و `public_html/storage` لازم است. معمولاً پوشه‌ها 755 و فایل‌ها 644 با مالک درست کافی‌اند؛ در صورت نیاز مالکیت را از پشتیبانی هاست پیگیری کنید. `.env` فقط برای حساب و PHP خواندنی باشد. نیازی به مجوز عمومی 777 نیست.

## دیتابیس بدون ترمینال هاست

این اصلاح سئو migration جدیدی ندارد؛ در ارتقای همین نسخه، دیتابیس فعلی را حفظ کنید و seed اجرا نکنید.

برای نصب تازه، یک MySQL/MariaDB آزمایشی مستقل روی کامپیوتر توسعه بسازید، برنامه را فقط به همان دیتابیس متصل کنید و migrationها را آنجا اجرا کنید. برای محتوای واقعی، خروجی مناسب دیتابیس موجود را استفاده کنید؛ seedهای نمونه جایگزین اطلاعات تجاری واقعی نیستند. خروجی SQL را از phpMyAdmin یا ابزار دیتابیس توسعه بگیرید و با phpMyAdmin سی‌پنل وارد دیتابیس تازه و خالی کنید. فایل SQLite محلی را به MySQL وارد نکنید. جدول `migrations` نیز باید منتقل شود.

در ارتقاهای بعدی که migration دارند، تغییرات را ابتدا روی کپی آزمایشی MySQL بررسی کنید و فقط SQL همان تغییرات تأییدشده را با phpMyAdmin اعمال کنید؛ دیتابیس زنده را با export نمونه یا دستورهای `fresh` و `reset` جایگزین نکنید. حساب‌های مدیر و محتوای واقعی را حفظ کنید.

## رسانه‌ها و فایل‌های دانلود

وقتی ساخت symlink روی هاست ممکن نیست، `PUBLIC_STORAGE_ROOT` را روی پوشهٔ واقعی `public_html/storage` بگذارید. محتویات فعلی `storage/app/public` یا مقصد symlink موجود را با File Manager/FTP به آن منتقل کنید؛ مسیرهای داخل دیتابیس نسبی‌اند و نباید بی‌دلیل تغییر کنند. آپلودهای جدید پنل مستقیماً در همین مقصد ذخیره می‌شوند. پوشه را در هر انتشار پاک یا با نسخهٔ خالی جایگزین نکنید.

فایل‌های خصوصی lead magnet در `sahra/storage/app/private` می‌مانند و از مسیر کنترل‌شدهٔ PHP تحویل داده می‌شوند؛ آن‌ها را به ریشهٔ وب منتقل نکنید. بسته رسانه‌های واقعی را حمل نمی‌کند. نبودن تصویر منبع همچنان 404 واقعی خواهد داشت؛ تصاویر اصلی، فونت‌ها و آیکون‌ها را روی هاست بررسی کنید.

## کش‌ها بدون ترمینال

بستهٔ تازه فاقد کش‌های وابسته به مسیر توسعه و سرویس‌های dev است. روی هاست با File Manager:

- فایل `public_html/hot` را، اگر از استقرار قدیمی باقی مانده، حذف کنید.
- فایل‌های تولیدشدهٔ قدیمی داخل `sahra/bootstrap/cache` مانند `config.php`، `routes-*.php`، `events.php`، `packages.php`، `services.php` و کش‌های Filament را پاک کنید؛ خود پوشه باقی بماند. Laravel فایل‌های لازم را دوباره می‌سازد.
- فایل‌های Blade کامپایل‌شدهٔ قبلی در `sahra/storage/framework/views` را پاک کنید؛ خود پوشه باقی بماند.
- هنگام انتقال از `CACHE_STORE=database` به `file`، کش محتوایی قدیمی استفاده نخواهد شد. در صورت باقی ماندن روی backend قبلی، کش‌های تنظیمات/منو/ترجمه را پاک کنید. برای backend فایل، فقط محتویات `storage/framework/cache/data` کش است.

پوشه‌های آپلود، فایل‌های خصوصی، دیتابیس و sessionها کش قابل حذف نیستند. روی کامپیوتر توسعه برای آپلود، `config:cache` و `view:cache` تولید نکنید؛ این خروجی‌ها می‌توانند رمزها یا مسیرهای محلی را حمل کنند. اجرای بدون کش تنظیمات برای این روش استقرار پشتیبانی می‌شود. اگر OPcache تغییر فایل را بررسی نمی‌کند، با ابزار سی‌پنل یا پشتیبانی هاست PHP را reload کنید.

## انتشار زمان‌بندی‌شده

انتشار دستی پنل و sitemap زنده به cron وابسته نیستند. رکورد با وضعیت `scheduled` فقط پس از اجرای فرمان انتشار به `published` تبدیل می‌شود. اگر Cron Jobs سی‌پنل و PHP CLI در اختیار دارید، از همان رابط سی‌پنل، هر پنج دقیقه این فرمان را با مسیر PHP واقعی هاست تنظیم کنید:

```text
/usr/local/bin/php /home/ACCOUNT/sahra/artisan sahra:publish-scheduled
```

اگر هاست امکان اجرای cron PHP هم ندارد، وضعیت انتشار را از پنل دستی تغییر دهید؛ انتشار خودکار زمان‌بندی‌شده نیازمند این قابلیت هاست است. برای دور زدن این محدودیت، endpoint عمومی اجرای فرمان یا migration ایجاد نشده است.

## بررسی پس از آپلود

- دامنهٔ اصلی را با مرورگر فارسی، حالت ناشناس و پس از انتخاب فارسی باز کنید؛ `/` باید با redirect دائمی 301 به `/en` برود. مسیرهای بدون زبان مانند `/about` هم به `/en/about` می‌روند؛ `/fa` و `/ar` به زبان خودشان باقی می‌مانند. `hreflang="x-default"` باید نسخهٔ انگلیسی همان صفحه باشد. کش قدیمی CDN/redirect را در صورت وجود از پنل مربوطه پاک کنید.
- `/en`، فهرست پروژه‌ها و مقاله‌ها، جزئیات منتشرشده و صفحات فارسی/عربی را باز کنید. در View Source متن اصلی و پایان مقاله باید داخل `main` باشد، نه فقط در JSON.
- با JavaScript خاموش نیز متن و لینک‌ها خوانا باشند؛ با JavaScript روشن فرم، منو، فیلتر و ناوبری داخلی را بررسی کنید. عنوان، description، canonical، hreflang و schema باید بعد از ناوبری عوض شوند و تکراری نباشند.
- یک تغییر آزمایشی مجاز در محتوای پنل انجام دهید و View Source تازه را بررسی کنید. مقاله/پروژهٔ پیش‌نویس و بخش مخفی نباید در پاسخ عمومی ظاهر شوند.
- `/robots.txt`، `/sitemap.xml` و sitemap زبان‌ها را باز کنید؛ دامنه صحیح و فقط URLهای عمومی منتشرشده وجود داشته باشند. sitemap در هر درخواست از دیتابیس ساخته می‌شود. `lastmod` حدسی تولید نمی‌شود.
- آدرس ناموجود و پیش‌نویس باید در Network پاسخ HTTP 404 بدهند. ورود پنل دارای `X-Robots-Tag: noindex, nofollow` است.
- HTTPS، هدایت www، تصاویر و مسیرهای رسانه، مجوز فایل‌ها، اتصال دیتابیس و SMTP را روی هاست واقعی بررسی کنید. آزمون محلی صحت تنظیمات زیرساخت هاست را اثبات نمی‌کند.

گزارش اصلاحات و تست‌های محلی در [SEO-REPORT-FA.md](SEO-REPORT-FA.md) آمده است. دربارهٔ رتبهٔ گوگل یا سرعت بدون اندازه‌گیری نتیجه‌ای اعلام نشده است.
